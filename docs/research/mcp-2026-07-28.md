# MCP 2026-07-28: skills, tasks and elicitation for `ikam mcp`

Question: what would `ikam mcp` (E359, E378, E388) have to do to ship skills, run long jobs as tasks and ask the person before risky steps, as the Model Context Protocol now allows? The plan that uses this note is `docs/plans/2026-11-24-mcp-skills-tasks-elicitation.md`.

## Read (2026-11-24)

These are specifications and product pages, not papers. Each line says what was read and what it claims. A claim is unverified for ikam until an experiment shows it with a real client.

- Anthropic, "MCP servers can now ship skills, run tasks, and more with Claude", 2026-11-24, https://claude.com/resources/articles/skills-over-mcp-tasks-and-more (full text). Skills over MCP in public beta in Claude and Claude Code, loaded only when needed; Tasks and Elicitation generally available; file uploads "rolling out soon"; the latest spec is stateless. No wire detail.
- Skills extension overview, https://modelcontextprotocol.io/extensions/skills/overview, and SEP-2640, https://modelcontextprotocol.io/seps/2640-skills-extension.md (full text; the SEP calls itself a historical record and points to the extension's own repository for the current text, not read).
  - Identifier `io.modelcontextprotocol/skills`, declared with the `resources` capability; one setting, `directoryRead`.
  - Methods: `skills/list` (cursor), `skills/get` (by URI), and the standard `resources/read`; `resources/directory/read` only with `directoryRead`.
  - A skill is a folder with `SKILL.md` at its root, frontmatter `name` and `description`; the folder's last segment equals `name`. Every file is a resource, by convention `skill://<skill-path>/<file-path>`.
  - Each listed skill is a full manifest: every file once, with `digest` (`sha256:` and 64 hex digits over the raw bytes) and `size`, or `"dynamic"` for generated content, which hosts may refuse.
  - Limits: at most 512 files and 16 MiB a skill. Hosts must not fetch a skill's files before it is loaded, must treat skill content as untrusted, and bind a user's approval to the file set (a changed digest asks again).
  - No change notification: hosts call `skills/list` or `skills/get` again.
- Tasks extension overview, https://modelcontextprotocol.io/extensions/tasks/overview, SEP-2663, https://modelcontextprotocol.io/seps/2663-tasks-extension.md, and the older core utility, https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks.md (full text of each).
  - Identifier `io.modelcontextprotocol/tasks`, for `tools/call` only. The client declares it in each request's `_meta`; the server decides per request and must never return a task to a client that did not declare it.
  - A task answer: `resultType: "task"`, `taskId`, `status`, `statusMessage`, `createdAt`, `lastUpdatedAt`, `ttlMs` (null for unlimited), `pollIntervalMs`. The task must be stored so that `tasks/get` resolves before the answer is sent.
  - `tasks/get` returns the state, with `result` when completed and `error` when failed; `tasks/update` sends `inputResponses` for the outstanding `inputRequests`; `tasks/cancel` is acknowledged and cooperative. Optional pushes: `notifications/tasks` after `subscriptions/listen`.
  - Statuses `working`, `input_required`, `completed`, `failed`, `cancelled`; the last three never change. A tool result with `isError` is `completed`, not `failed`.
  - Ids must be unguessable; when there is an authorization context, tasks are bound to it. No `tasks/list` and no `tasks/result` in the extension (both are in the 2025-11-25 core form, which is not wire-compatible with it).
- Elicitation, https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation, and multi round-trip requests, https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr (full text).
  - A server asks during `tools/call` (also `prompts/get`, `resources/read`) by answering `resultType: "input_required"` with `inputRequests` (here `elicitation/create`) and an opaque `requestState`. The client retries the same call, with a new JSON-RPC id, the answers and the same `requestState`. Server-initiated requests are no longer allowed.
  - Two modes the client declares: `form` (a flat schema of strings, numbers, booleans and enums) and `url` (the person opens a link the server gives). Form mode must never ask for passwords, keys or tokens.
  - Answers: `accept` with content, `decline`, `cancel`.
  - `requestState` is attacker-controlled: protect it with a MAC or AEAD when it matters, bind it to the principal, a short TTL and the request; single use is the server's job.
  - For URL mode the server must check that the person who opens the link is the person who made the request.
- Base protocol, https://modelcontextprotocol.io/specification/2026-07-28/basic/index, versioning and `server/discover` pages (full text).
  - The protocol is stateless: every request carries `_meta` with `io.modelcontextprotocol/protocolVersion` and the client's capabilities; there is no handshake, and an open stdio process is not a session.
  - Servers must implement `server/discover` (supported versions, capabilities and extensions, server info, instructions).
  - An unsupported version is error -32022 with the supported list. `initialize` remains for 2025-11-25 and earlier, and a dual-era server may serve both.
- Anthropic, "Bringing MCP 2026-07-28 to Claude", https://claude.com/resources/articles/bringing-mcp-2026-07-28-to-claude (full text). Moves MCP to request and response; support rolling out across Claude products.
- Claude Code MCP documentation, Spanish edition, https://code.claude.com/docs/es/mcp. Read up to where the page text ended for the fetcher. The sections on skills, tasks and elicitation were not in that text. What was read:
  - a client runtime that speaks 2026-07-28, with a setting that keeps stdio servers on the older protocol;
  - a long call moved to the background after 2 minutes;
  - a stdio call with no answer and no progress aborted after 30 minutes;
  - tool output warned at 10,000 tokens and capped at 25,000 by default;
  - a call waiting on an open elicitation is not moved to the background.

## Hypotheses

- H1 (M1): one dispatcher can serve 2026-07-28 requests and `initialize` clients over the same handlers with no change to today's answers. Source: versioning page. Status: open.
- H2 (M2): moving usage guidance into a skill cuts the bytes every session pays at start, and store-held skills follow commits and shares like any file. Sources: skills extension; E359's characters per task. Status: open.
- H3 (M3): task state kept as a Petri net in the store gives the spec's durability and its fixed terminal states by replay, with nothing acknowledged lost on a kill. Sources: tasks extension; E386's kill test. Status: open.
- H4 (M4): a MAC'd, single-use `requestState` makes a confirmation hard to forge or replay. Form mode confirms intent only; URL mode with sign-in on the server's own page can carry an authorization. Sources: elicitation and MRTR pages. Status: open.

## Unknowns
