# A self-improvement loop on IKAM (E400)

The owner asked for a recursive self-improvement loop run via IKAM to improve IKAM itself. This plan says what the loop is, what it may change, what it may not, and how it fits the nightly loop net (E386).

## Two levels, one net

- **Level 0, the kernel.** A candidate is one change to the kernel, committed on its own branch (`exp/400-cand-*`). The first version's candidates are one catalog constant changed by one line (`experiments/self-loop/catalog.tsv`, the tunables the experiments README names, as E322 used them). Each is measured by a fixed procedure and kept or closed.
- **Level 1, how the loop picks.** A ranking policy orders each round's candidates: a weight per feature read from the loop's own history (how much this constant moved the north score before, how often it improved or worsened it, whether the new value lies on the side of a value that helped, the size of the step, whether it was never tried, its usual test time). After a round, a meta step proposes variants of the policy and adopts one only if it ranks held-out rounds better. The meta step also changes its own search radius (wider after an adoption, narrower after a rejection), so the search that improves the picker is itself adjusted by results.
- **One score for level 1:** changes kept per test-hour, `fixed.kept_per_hour`: kept changes found in the first half of a pool's total test time, and the area under the kept-against-hours curve. Test time is everything the machine spends on a candidate: build, benches, tests.
- **State on IKAM.** Everything is a firing of the `self` net (`examples/self_loop.rs`) on an FsStore, ref `loop/self`. Candidates go through `propose`, `start` (holds the cpu token), `finish` (output: the measured result) and `keep` (to `waiting`) or `close`; `merge` is a human transition the loop never fires. Policies go through `variant` (output: the policy and its held-out score) and `adopt` or `reject`; the policy in use is `retire`d when another is adopted. The loop reads its history back from the firings and keeps no other state, so a killed round resumes from the store and every step replays (E269, E386).

## What the loop cannot change

In `experiments/self-loop/fixed.py`, which the loop imports and never writes:

- the scoring: the two scores, their tolerances and the keep rule (north better beyond 0.5% on the north-only run and both full runs, cost not worse beyond the larger of 2% and the round's base spread on both, as E322's analyze.py applies the README rule), the hard gates (the bench's byte-exact reconstruction and fsck, then `cargo test --release` for a kept change);
- the evaluator that judges a policy;
- the guards: a candidate's diff must be exactly the catalog line with only its value changed (`check_diff`), protected paths (tests, `examples/bench.rs` and its common code, the catalog, `fixed.py`, `Cargo.toml` and the lock file, `.github`, the experiments README) are hashed at the start of a round and checked before every verdict, branches the loop writes must match `exp/400-(self-loop|cand-*)`, and a stored policy may hold only weights, a radius and a seed (`check_policy`).
- main: the loop pushes nothing and merges nothing. Kept candidates wait in `waiting` for the owner's merge, a human transition.

`experiments/self-loop/guard_test.py` checks that each guard refuses what it should.

Not a candidate: `ARCHIVE_READS` in the bench (E322 tried it), because it changes the north score's weights, which is the scoring.

## The test procedure

North first, because the north score is deterministic (bytes only) and a north-only run takes about 104 s here, against 232 s for a full run:

1. build the bench (about 30 s incremental);
2. the three north corpora alone; worse beyond 0.5% closes the candidate, flat closes it too (a flat-north change could only be kept for a cost win, and on a cloud machine the cost score's own spread is 2-5%, E322);
3. north better: two full runs, the keep rule on both;
4. kept: `cargo test --release`.

## How it plugs into the nights

The nights' net (E386's `loop_drive`, the trip-week plan) drives agent-written experiments; this loop drives machine-made candidates. They can share a night without sharing state:

- A night gives the loop a slot in its plan: one pick, `self-loop round`, whose `finish` output is the round's score. The night net's `cpu` token is held for the round, so the two never bench at once.
- The loop's policy can rank the night's own picks too once those picks record the same features (constant or mechanism, test time, verdict); that is the next step, not this version.
- Kept candidates are options like any other night's keeps: they wait for the owner.

## Limits of the first version

- Candidates are one-line constant changes from a fixed catalog, not code an agent writes. An agent-made candidate would enter as a `propose` firing with its diff as the output, through the same guards (protected paths, own branch), but the one-line rule would have to become a path rule.
- The seed history is small (22 results from E322, E347 and E348, test time modelled), so the first policy is fitted to two held-out rounds and may be overfitted. Round 1 measures it on candidates it has not seen.
- A round measures its whole pool, so the fixed ranking and the policy can be scored on the same results; a production round would stop at its budget.
